# Beta release checklist

<!-- release-checklist-schema:1 required-items:77 -->

A release is ready only when every applicable item has direct, reviewable
evidence. Link the command log, CI run, test record, screenshot or decision
record beside each checkbox. “Implemented,” “tested locally,” or a broad green
CI badge is not evidence unless the linked check covers this release and this
requirement.

Publication and tester invitation are separate gates. Before a release
candidate can be published, every pre-publication item must be checked with
direct evidence, product intake and the beta runbook must be complete, release
notes must describe the actual product, a reviewed License must exist, and the
machine-readable release decision below must record `GO`. Items that inherently
need the published immutable URL remain open until the post-publication pilot
gate; they cannot be filled with circular or predicted evidence.

| ROLLBACK — target release and communication | ___ |

The default is **HOLD** when evidence is missing. A deadline does not turn an
unchecked item into “not applicable”; the release owner must state why it is
not applicable to the actual distribution and product promise.

After recording the decision, the release owner changes `RELEASE_STATUS` from
`HOLD` to `GO` in the reviewed release commit. The tag workflow calls
`bash scripts/release-readiness.sh --require-go`; a tag cannot bypass HOLD.
The final tag commit and artifact hashes are written by the workflow into
`RELEASE-METADATA.txt`, `SHA256SUMS`, and GitHub's immutable release record;
they are not embedded as a self-referential hash inside their own source
commit.
